# Restore epoch contract, held

Application restore entry points are direct backup POST and chunked uploadCommit. Recovery snapshots are exported and submitted through the same backup restore route. They all call persistSpace(owner,current,next,true). The SQL implementation locks the current owner state row, checks the current revision, writes entity diffs, and then writes metadata and current revision+1 in one transaction. The old backup revision is never imported.

persistSpace now replaces next.generation with a fresh server-generated UUID string for every restore=true call, including direct supported internal callers with no changed invoice rows. It does not mutate the caller's supplied state. The central wrapper also passes this epoch to the existing Firestore path, but SQL derived-table tests do not establish Firestore acceptance.

Metadata is stored as JSON text in gymos.gym_states.payload. The field is generation, optional string before restore and UUID string afterward. The shared refs migration must compare OLD.payload::jsonb -> 'generation' and NEW.payload::jsonb -> 'generation' with IS DISTINCT FROM and invalidate affected owner readiness atomically in a trigger-only scope. This hook is owned by the refs worker and remains a separate acceptance gate. No application DML privileges on derived tables are requested. Readiness must remain absent after the final metadata UPDATE, until an authorized exact rebuild and verification. A later normal insert must not claim a previously restored populated owner ready.

The held190000 owner-version trigger already bumps a monotonic sequence-backed version on every gym_states UPDATE, including an otherwise unchanged restore. Entity and photo changes also bump it. Live version-keyed caches therefore see a changed token at commit; readers without a live token must refuse cache use. Invalidating only in-process maps would not cover another instance and is not the contract.

PGlite tests cover no-entity-diff restore with a new epoch/token, two successive restores, stale revision refusal, another owner's token remaining unchanged, caller input immutability, ordinary save preserving epoch, and injected pre-COMMIT failure rolling back epoch, revision and version together. These tests do not prove the pending refs invalidation trigger, deployment, concurrent snapshot semantics or hosted runtime grants.

Repository source scan found no other supported application full-payload restore writer outside persistSpace. Demo seeding uses the normal persistSpace path. Raw operational imports, disabled triggers, table replacement and whole-database restores are separate operational flows: stop readers, invalidate readiness and cache epochs before reopening, and verify source/refs consistency. This document does not authorize those actions or treat a superuser's ability to bypass triggers as an application guarantee.
