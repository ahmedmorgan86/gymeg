# Private member credit correctness fallback, held

This is a correctness candidate independent of allocation refs. It does not complete demand loading or reduce invoice scan work. The private scalar uses unchanged memberCredit over every owner invoice's allocations and voided fields, including unrelated rows that affect legacy JavaScript string arithmetic. Only the number is passed separately to memberView; foreign invoice payloads are never added to returned portal state. Account invoices/payments remain own-member only.

PostgreSQL portal code-session, linked Google and staff-preview paths all use readMemberSpace's same private credit override. Live owner version is read before hydration and rechecked before/after money, with metadata revision matched to hydrated revision. Missing version, raced writes, unsupported/nonfinite arithmetic, ambiguous tied invoice positions and more than10,000owner invoices refuse. Portal route surfaces503unavailable, not the old sliced credit. Account returns503with reason. No stale-money fallback is used.

The10,000invoice admission cap is provisional engineering scope, chosen after the initial5,000cap refused the existing10,000invoice native fixture. It is not capacity acceptance or evidence that all owners are supported. Large-owner refusal remains a full-functionality gap. The helper limits returned projections, not necessarily database rows scanned. Each read uses the bounded read-only transaction helper with at-most2second statement timeout and shared4second clock. Portal hydration and authentication are still unconverted and can exceed that clock; when they return late the money read refuses. No whole-portal lifetime claim is made.

Firestore takes existing full readSpace for credit correctness instead of sliced hydration in this candidate. This is untested and may increase work.
