# تقييم تطبيقات GymEG وتنبيهات Push — 3 نوفمبر 2026

## الحكم

التطبيقات ليست جاهزة بعد لوصفها بأنها مكتملة تجاريًا أو بلا أخطاء. جودة منطق البيانات والصلاحيات جيدة في الفحوص المحلية، لكن Push لم يصل إلى الإنتاج بعد، ولم تُختبر تطبيقات Android على أجهزة فعلية، كما أن Push الأصلي بالخلفية لا يتوفر قبل إعداد Firebase. لا يوجد اختبار براءة من العيوب؛ هذا التقرير يحدد ما ثبت وما بقي.

## ما أُنجز

- إضافة Web Push لمحادثات النادي: رسالة العضو تنبه مالك/مدير الفرع؛ رد الإدارة ينبه العضو المعني فقط.
- نص التنبيه عام ولا يضم محتوى المحادثة أو اسم العضو. حفظ الاشتراك مشفر بـAES-256-GCM؛ معرف نقطة الإرسال المخزن هو SHA-256. القبول محدود بمزودي دفع المتصفح المعروفين، والاشتراكات المنتهية تُحذف عند رد HTTP 404/410.
- عزل الاشتراكات بحسب النادي/المالك والفرع والدور. أُنشئ جدول `gymos.push_subscriptions` في Supabase مع تفعيل RLS وفرضها وسياسة `app.gym_owner`، ومنح الوصول لدور runtime المحدود فقط.
- أُضيفت أسرار VAPID ومفتاح تشفير الاشتراكات إلى متغيرات Vercel الإنتاجية كقيم سرية عند الحاجة. لم تُدرج الأسرار في المستودع أو الحزم.
- تم تحديث دليل التنبيهات والمراجع العربية والإنجليزية وإعادة توليد الأدلة السبعة.

## حالة الإنتاج

- قاعدة Supabase: الجدول والسياسة موجودان، وRLS مفعّل ومفروض.
- إعدادات Vercel: متغيرات Push الأربعة موجودة في production؛ القيم السرية لم تُقرأ أو تُعرض.
- الموقع الحي: `GET /api/push-subscriptions` أعاد 404 وقت المراجعة، لذا كود الاشتراك والإرسال غير موجود بعد في النشر الحالي. إعدادات الخادم وحدها لا تفعّل الميزة.
- لم تُرسل رسالة حقيقية أو إشعارًا إلى عضو حقيقي، ولم يُجر اختبار Push من مزود خارجي.
- الكود المحلي على الفرع `fix/community-message-notifications` ما زال تغييرات عمل غير منشورة. لا تُعتبر نسخة الموقع الحالية محدثة بها.

## حدود Push والمنصات

- Web/PWA: Push يعتمد على نشر الكود وموافقة المستخدم ودعم المتصفح ومزود الإشعار. قبول المزود للإرسال لا يثبت أن المستخدم شاهد التنبيه.
- Android الأصلي: الـWebView الحالي لا يكفي لتسليم إشعار بعد إغلاق التطبيق. دمج Firebase Messaging يحتاج مشروع Firebase وتكوين كل package ومفتاح خادم موثوق؛ التوثيق الرسمي: [Firebase Cloud Messaging](https://firebase.google.com/docs/cloud-messaging).
- Windows WebView2: مسار الإشعار المحلي موجود عند تشغيل التطبيق؛ Push في الخلفية لم يُثبت على WebView2 الفعلي.
- السماع والصوت وقارئ الباركود والكاميرا واختبارات تثبيت APK/Windows على أجهزة العملاء ليست ضمن هذه الجولة.

## الملاحظات ذات الأولوية

1. نشر الفرع بعد مراجعة واعتماد المستخدم؛ بعدها يجب أن يرجع endpoint إنتاجي 200 مع `configured: true` دون كشف المفتاح الخاص.
2. إجراء اختبار Push حي باستخدام عضو ومدير تجريبيين وعلى جهازين، والتحقق من الفرع وصحة الإلغاء وانتهاء الاشتراك.
3. توفير إعداد Firebase للتطبيقات الأصلية الثلاثة إن كان المطلوب وصول تنبيه عند إغلاق APK، ثم إعادة بناء APKs وتحديث حزم التنزيل.
4. اختبار Windows WebView2 والإشعارات الفعلية على جهاز المستخدم. لا تستبدل هذه التجربة نجاح البناء أو اختبارات DOM.
5. تشغيل تدقيق ثغرات npm وNuGet باتصال مسموح، ثم مراجعة إعدادات تسليم App Store/Google Play والشهادة قبل البيع التجاري.

**الخلاصة:** لدينا أساس ويب آمن ومختبَر محليًا، وتجهيز Push في Supabase وVercel، لكن الإصدار المنشور لا يحتوي endpoint الجديد بعد، وتطبيقات Android الأصلية لا تزال بلا Firebase. لذلك الإجابة العملية: التطبيقات جيدة من جهة الاختبارات البرمجية، لكنها ليست جاهزة للنشر التجاري النهائي أو لإعلان Push الكامل حتى إغلاق البنود أعلاه.
